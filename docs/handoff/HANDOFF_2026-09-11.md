## 2. Working rules to know before touching anything

1. **Claude does not run git commands.** Running them through device bash once left a stale `.git/index.lock` that device bash cannot delete (it cannot delete files at all, only `mv`). Claude writes the commands and the user runs them. To read git state, read files under `.git/` directly (`.git/HEAD`, `.git/refs/...`, parse `.git/index` in Python) - that is safer.
2. **Commits must not carry `Co-Authored-By: Claude`.** The user wants `Kimmy213` alone as the author. This was got wrong once and needed an amend plus a force push.
3. **Always tell the user before editing `SODA_BASELINE.md`**, and every edit must bump the version number and add a row to the revision history (version, date, what changed, which sections, who). That rule is written into section 9.4 of the document itself.

## 3. What SODA is, briefly

**S**ampled-**O**bservation **D**emand-**A**daptive: a controller that sees the world as a real camera does, **counting vehicles every 2 seconds**, with no tracker, no idea which vehicle is which, and no idea when any of them arrived.

- the junction has 7 movements but **4 signal heads**: `H_A` (controlling A and A2), `H_B`, `H_Bx`, `H_CB`
- states: `ALL_RED_IDLE -> COLLECT (7 s ceiling) -> SERVE`
- four decision steps: **Q1** a starving head (waited >= 42.75 s) -> **Q2** leader = oldest queue -> **Q3** group everything that can go at once -> **Q4** `G = clamp(max(2.95 + D x 2.31), 8, 45)`
- three interrupts: gap-out (two consecutive zero readings), anti-starvation, max green 90 s
- the Fixed comparator: a 106 s cycle (40/20/31 plus 3+2 intergreen three times)

**The full specification is `SODA_BASELINE.md`, which is the real reference document.** Every statement in it is tagged `[code]`, `[test]`, `[measured]` or `[tuned]` to say how it was verified. Where the document and the code disagree, **the code wins** and the document must be corrected.

Values measured in the field (never change these without re-running): l1 = **2.95 s**, h = **2.31 s/veh** (39 samples), saturation flow 1,558 veh/h/lane, detector 98.3% (298/303), A2 share = 5.4%, shared lane 32 m.

## 5. Batch v1 results and bug C1

### 5.1 The numbers (keep these as the "before" half; do not cite them as results)

| Scenario | Fixed | Adaptive | difference | t (df=26) |
|---|---|---|---|---|
| MorningPeak | 22.77 +/- 0.97 | 14.11 +/- 0.61 | +8.66 (38.0%) | +38.2 |
| MiddayNormal | 22.66 +/- 0.89 | 14.78 +/- 0.75 | +7.88 (34.8%) | +41.8 |
| ABACEvent | 93.35 +/- 6.45 | 67.26 +/- 14.13 | +26.10 (28.0%) | +8.3 |
| EveningPeak | 25.40 +/- 0.72 | 25.95 +/- 1.57 | -0.55 (-2.2%) | -1.8 |

**Never write that EveningPeak "lost".** The critical value at df = 26 is 2.056, so t = -1.8 is **not significant**. The correct wording is "the means do not differ significantly". (Itim's warning: write "lost" and an examiner who checks the arithmetic will catch it.)

### 5.2 Bug C1 - the Unity code did not follow the specification

`SODA_BASELINE.md` section 4 says `phase end - for each served head: queueStart = now`, meaning **every head that just had green**. But `ServeOnePhase` called `ResetQueueStartFor(dropping)`, covering only the heads turning red. A head that continued across phases therefore held a stale clock indefinitely and won both Q1 and Q2 forever.

**The main evidence (use this in the report, not the single case)**

| EveningPeak - `MaxWaitTime` per run | min | median | max |
|---|---:|---:|---:|
| Adaptive | **126.5** | 188.3 | 344.4 |
| Fixed | 92.7 | 96.3 | **103.9** |

Adaptive's best run is worse than Fixed's worst, and it exceeds the ceiling in 27 runs out of 27, with `maxWaitTime` set to 45 seconds.

Supporting evidence: `phases_Adaptive_EveningPeak_Rep17` from t = 1104.6 to 1470.2 is **365.5 seconds in which H_CB got no green at all**, with H_B in the group for 24 consecutive phases. Rep17 has 99 phases but logged 137 `StarvationEvents` (L13 notes that this counter double-counts, so about 68 real events). **The figure 145 is the median across the 27 runs, not Rep17's own value - do not confuse them.**

**Whose fault:** specification section 4, correct. Itim's `soda.py` (`end_phase` iterating `for h in self.green`), correct. **The C# alone was wrong.** So this is not an algorithm change and needs no vote under section 9.1, but it still requires a fresh batch under section 9.3.

### 5.3 What was fixed (merged 11 Sep)

- **C1** added `ResetContinuingHeads(servedLastPhase, dropping)` to `ServeOnePhase` after turning green
- **C2** `ForceStop()` now clears the SODA counters - Fixed rows in `summary_all_runs.csv` used to carry the previous Adaptive run's values (107 of 108 rows matched exactly)
- **C3** moved `phaseCounter++` above the `showDecisionPanel` early return - `PhaseIndex` used to be 0 throughout a batch file

Itim reproduced the cause himself in Python with `test_queueclock.py`: 10 phases in permanent saturation gave leaders `A Bx CB A Bx CB A Bx CB A`, served A 4 / B 7 / Bx 3 / CB 3, with no lock-out.

## 9. Traps already hit; do not step on them again

1. **Unity's serialized scene values override the script defaults.** Editing the `.cs` does nothing if the scene holds an old value. Run `ABAC > Verify Scene Against Code` after every value change.
2. **A test comparing `.cs` against `.cs` cannot catch a serialization bug.** It has to compare against the real `.unity` file.
3. **A test that does not walk every path.** `SodaTest` section 1 really does test the queueStart reset, but it sets the scene up by dropping that head to red every phase - the path the code already handled correctly. It passed throughout while the bug existed. When writing a test, ask which path has *not* been walked.
4. **`summary_all_runs.csv` appends silently.** Always move the old results out before a new run.
5. **High timeScale used to make cars overshoot lanes.** If that returns, sub-stepping is broken or has been removed; look at `CarAgent.MAX_STEP`.
6. **Unity once crashed in IMGUI during a batch** (`GUIScrollGroup.CalcWidth`). Fixed by hiding the panel with nested scroll views during a batch. If it crashes again, look there.
7. **Do not push to the wrong folder.** See 1.2.
