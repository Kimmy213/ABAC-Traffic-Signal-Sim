ABAC Smart Traffic Light · Module C · Unity digital twin

How the 19 files work together

The simulator is 19 C# files: 16 that run in Play mode and 3 Editor tools that build the scene. This page shows what each file does and how they connect. Each file then has its own page, which starts with the whole file and then goes into its parts and every variable.

On this page

The junction being simulated

The ABAC entrance on Bangna-Trad Road is a T-junction with seven movements and four signal heads. Everything below is drawn from the constants and waypoint tables in ABACSceneBuilder (x runs east, z runs north, in metres). Who calls whom

Each arrow is a real reference in the code: a method call, a field of that type, or a FindFirstObjectByType. Names that only appear in comments are left out. UITheme is used for drawing by nine files, so it has no arrows; see its page. Start with the simulation path, then switch on the other two sets.

The simulation path

Cars come from CarSpawner and drive as CarAgent. A ROIZone counts them. A controller, Fixed or Adaptive, turns that count (or nothing, for Fixed) into TrafficLight states, and the light tells the cars. IntersectionConfig is the shared description of the junction that every part looks lanes up in.

The measurement path

ROIZone reports each car's wait to DataLogger as it leaves the zone, and AdaptiveController reports each phase. ScenarioManager drives 216 runs and asks DataLogger for the results. The controller itself never reads the measurement.

What runs when

Unity calls a few methods on every component at fixed moments. The table lists what each file does at each one. The order of Awake calls between components is not guaranteed, so files that depend on IntersectionConfig call its EnsureBuilt() themselves.

MomentWhat happens
AwakeIntersectionConfig.Build builds the conflict matrix · AdaptiveController enforces the measured 2.95 / 2.31, then groups lanes into heads · FixedController resolves lane names to signal indices · ScenarioManager enforces a2Share = 0.054 · DataLogger.Instance = this · the panels find their references
StartBoth controllers start at Play: Fixed starts RunCycle, Adaptive starts SnapshotLoop and RunSoda · CarSpawner starts its spawn loop unless the panel already did · CarAgent loads its driver profile · SimulationControlPanel.StartRun (with autoStartOnPlay) then stops both controllers and restarts only the selected one
UpdateCarAgent moves in ≤ 0.02 s sub-steps · SimulationControlPanel advances the run clock and stops it when the road is clear · RoiHighlight keeps its box in sync
PhysicsROIZone.OnTriggerEnter / Exit when a car's collider crosses a zone boundary (the car carries a kinematic Rigidbody so these fire)
LateUpdateCameraDirector eases the camera towards the current shot
OnGUIEvery panel draws itself, wrapped in UITheme.Begin / End; key presses are read here too
CoroutinesSnapshotLoop, RunSoda, RunCycle, SpawnLoop, PendingReleaseLoop, DespawnWhenFar, RunAllExperiments: long-running loops that wait with yield

A single run (control panel)

  1. ApplyTestCase sets each lane to Poisson or a schedule
  2. Seed: randomSeed for Poisson cases, a fixed 20260820 for scripted ones
  3. ResetAllLanes(seed) clears every lane, then reseeds and restarts it
  4. DataLogger.ResetRun
  5. ApplyController: stop both, enable one, RestartCycle
  6. Scripted cases stop the clock when every car is released and the road is empty

One run of a batch (ScenarioManager)

  1. seed = StableHash(scenario) + rep × 31, the same for Fixed and Adaptive
  2. Poisson rates for the scenario, then ResetAllLanes(seed)
  3. Stop both controllers, enable one, restart it
  4. 120 s warm-up, then clear the data
  5. 1,800 s measured at 10× speed
  6. Record the result, write three CSV files

The scene overrides the code

Read this before any variable table. When a component sits in SampleScene.unity, Unity saves the value of every public field into the scene file. On load, those saved values replace the defaults written in the .cs file. Editing a default in code therefore changes nothing for a component already in the scene.

That is fine when it is deliberate, as with the per-lane spawner settings. It has also gone wrong: the scene once held startupLostTime = 1, saturationHeadway = 2.5, repetitionsPerScenario = 1 and a2Share = 0.18 after the code had moved on (the header of SceneParameterAudit.cs). Three guards now stop that from reaching a result:

  1. Constants as the source of truth. MEASURED_STARTUP_LOST_TIME, BATCH_REPETITIONS and the like cannot be overridden, because const fields are never saved into the scene.
  2. Correct on load. AdaptiveController.EnforceMeasuredParameters and ScenarioManager.EnforceMeasuredShare run in Awake, put the measured values back and log an error.
  3. Check the file. SceneParameterAudit compares the scene with the code inside Unity, and SceneAuditTest reads SampleScene.unity itself in the test suite.

Every variable table on the file pages has a Saved value column read from SampleScene.unity, or from Car.prefab for CarAgent and RoiHighlight, which live on the car prefab. Values in red differ from the code default. For the controllers and ScenarioManager there are none, as of this build.

How to read a file page

Every file page follows the same order. It opens with the big picture: the file's job, where it sits, and an outline of its methods. Then comes the deep dive, one section per group of methods, each with the real code and its line numbers. It ends with the variable table and a list of known issues. Each claim about changing a variable is marked with what it rests on:

measured a recorded result exists and is cited from the code it follows directly from the code; not measured unknown depends on traffic and has not been run

Numbers come from three places only: the code, the baseline documents (docs/soda/SODA_BASELINE.md and docs/unity/Unity_BASELINE.md), and batch v5 (SimulationResults/batch_v5).

What the simulator produced

Batch v5 (1-2 Oct 2026): 216 runs, 108 Fixed/Adaptive pairs on shared seeds. Across all four scenarios, SODA cut the mean wait from 42.03 s to 33.62 s (−20.0%, paired t-test p = 1.2 × 10⁻⁸) and the worst wait in a run from 204.2 s to 119.3 s (−41.6%).
