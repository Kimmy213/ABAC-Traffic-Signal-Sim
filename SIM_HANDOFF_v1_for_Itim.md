## 1. What the simulation is

Unity 6 (6000.5.4f1), Built-In Render Pipeline, C# MonoBehaviour architecture. It is a **behavioural** digital twin, not a visual one: cars are kinematic agents with car-following, queueing, a stop line, and a signal state; the geometry is to scale from the real junction.

Everything in the scene is generated by a single Editor script (`ABACSceneBuilder`) from named constants, so the geometry can be corrected from field data by changing one number — nothing is placed by hand.

Two controllers run against **identical** traffic (same seeded RNG per lane), so any difference in the results is caused by the signal logic alone.

## 2. The seven lanes

| Lane | Movement | Signalised? |
|---|---|---|
| **A** | Bang Na–Trad **eastbound** (+X), straight through — **inner** lane | ✅ own light |

| **B** | Bang Na–Trad **westbound** (−X), straight through | ✅ own light |

| **CA** | Exits ABAC, **left turn** east, merges into A — free movement | ❌ unsignalised |

The eastbound approach has **exactly 2 physical rows**: A (inner) and the shared Ax/A2 (outer). CA and CB are separate physical lanes on the ABAC exit (x = 3.8 and x = 1.5).

### Conflict matrix (6 conflicting pairs)

`A↔Bx`, `A↔CB`, `A2↔Bx`, `A2↔CB`, `B↔CB`, `Bx↔CB`

Deliberately **not** conflicting, so they can be green together:
- **A ↔ B** — opposing straight movements
- **B ↔ Bx** — same approach, protected right turn
- **A ↔ A2** — physically the same signal head

## 4. Two mechanisms that are easy to miss

### 4.1 Shared-lane blocking (A2 blocks Ax)

A2 and Ax occupy **one physical outer lane**. When A is red, A2 stops at the stop line and physically blocks Ax behind it, even though Ax itself has no signal.

Modelled as a **late merge**: A2 does not enter the shared lane far upstream, it merges only ~5 car-lengths before the stop line — so it arrives at the **head** of the queue. The resulting blocking is **infrequent but near-maximal**, not frequent-but-mild. That distinction changes the delay distribution's shape, so it matters for the results.

A2's share of straight traffic entering the outer lane = **5.4 %** — your direct count in `SP1_HANDOFF_v2` §5, which supersedes the earlier 18 % back-calculation. Implemented as Poisson thinning: `interval_sub = interval_combined / share`.

Shared-lane length = **32 m (~5 vehicles)**, your §5.6. The lane change is now constrained to happen entirely inside that 32 m: steering begins exactly at the 32 m boundary and the merge completes 20 m before the stop line. Previously it began 42 m out — 10 m upstream of where the shared lane actually exists.

> **Correction to the earlier draft of this brief:** it quoted 18 % throughout. The scene file was also still carrying 0.18 while the code used 0.054. Your figure for what that costs — **26 % of cycles blocked at 5.4 % vs 66 % at 18 %, a 2.5× overstatement of the mechanism §5.6 is built on** — is why this mattered more than a stray constant. Both are now on 5.4 %.

### 4.2 Ax yields to Bx ("inverted light")

Ax and Bx both turn into ABAC, from opposite directions. Ax **cannot** turn in while Bx is green.

Implemented as a new concept, `lightIsInverted`: Ax reads **Bx's** light inverted — Bx green or amber = Ax red. Ax is therefore constrained without ever being given a phase or appearing in the conflict matrix.

### 4.3 Shared ROI

Ax and A2 share **one ROI object** — this is what a single real detector on that lane would actually see. Per-lane statistics survive because the logger records `car.assignedLane`, not the ROI's name.

## 5. Adaptive controller — the timing formula

Green time is recomputed every phase from the vehicle count in the ROI at that instant.

$$
G = \mathrm{clamp}\big(\ell_1 + D \times h,\; g_{\min},\; g_{\max}\big)
$$

| Symbol | Meaning | Value | Source |
|---|---|---:|---|
| $\ell_1$ | startup lost time | **2.95 s** | **your field measurement** (39 samples, 5 saturated greens, lane B morning) |
| $h$ | saturation headway | **2.31 s/veh** (sd 0.81) | **your field measurement** |
| $D$ | vehicles in the critical lane's ROI at phase start | runtime | `ROIZone.GetVehicleCount()` |
| $g_{\min}$ | minimum green | 8 s | practice |
| $g_{\max}$ | maximum green per phase | 45 s | practice |

For a concurrent phase (several lanes green together), lanes discharge **in parallel**, so the **critical lane** sets the time:

$$
G = \mathrm{clamp}\Big(\max_{i \in \text{group}} \big(\ell_1 + D_i \, h\big),\; g_{\min},\; g_{\max}\Big)
$$

Inverse form, used throughout the analysis: $N = (G - \ell_1)/h = (G - 2.95)/2.31$

**Local saturation flow:** $s = 3600/h = 3600/2.31 = 1{,}558$ veh/hr/lane — **13 % below** the HCM default of 1,800. Using our own measured values instead of the textbook ones is one of the project's main claims.

### Where the formula saturates

| $D$ | $G$ |
|---:|---:|
| ≤ 2 | 8 s (floor) |
| 3 | 9.9 s |
| 5 | 14.5 s |
| 10 | 26.1 s |
| 18 | 44.5 s |
| ≥ 19 | 45 s (ceiling) |

Linear range is $D = 3\ldots18$ vehicles.

### $G$ is only a ceiling

$$
G_{\text{effective}} = \min\big(G,\; t_{\text{gap-out}},\; t_{\text{starvation}},\; t_{\text{max-green}}\big)
$$

| Mechanism | Cuts the phase when | Parameter |
|---|---|---|
| Gap-out | every lane in the group is empty for `gapOutDelay` | 3 s |
| Anti-starvation interrupt | green ≥ 20 s **and** another lane has waited ≥ 0.90 × 45 = 40.5 s | `minGreenBeforeInterrupt` = 20 s |
| Max continuous green | same group green for 90 s **and** demand exists outside it | 90 s |

### Decision order each phase

1. Wait for demand (if the whole junction is empty → **rest in green**).
2. Pick the leader lane: **starvation override first** (any lane waiting ≥ 0.95 × 45 = 42.75 s), otherwise **FCFS** — the lane whose *oldest* waiting vehicle arrived first (not the lane with the most cars; that would starve small lanes).
3. **Counting window:** if the leader has < 3 vehicles, wait 4 s to accumulate demand, then re-pick.
4. Build the concurrent group: add non-conflicting lanes with ≥ 1 vehicle, oldest-arrival first. Lanes sharing one physical signal head (A/A2) are always forced into the same group.
5. Clearance: 3 s yellow + 2 s all-red **only for lanes that must turn red**. Lanes staying green are not cut — this saves 5 s of intergreen on every overlapping group, which Fixed can never do.
6. Compute $G$, run the green phase with the three interrupts above.

**Why Adaptive wins, in three lines:** (1) no wasted green on empty lanes, (2) intergreen not paid when phases overlap, (3) time allocated to the lane that actually has the queue. **What it costs:** no predictable cycle length for drivers, and it needs a reliable detector on every lane — which is why the starvation and max-green guards exist.

## 8. What is modelled vs. what is not

**Modelled:** conflict-matrix signalling, concurrent phases, shared-lane blocking with late merge, Ax yielding to Bx, per-lane driver-behaviour mix (aggressive / normal / cautious), queue spillback, a pending-arrival queue so demand is never silently dropped.

**Deliberately not modelled — these belong in the report's limitations section:**

1. **The emergency/escape-lane bypass is disabled.** Enabling it let cars pass through one another, and the 5.4 % A2 share already absorbs part of the same effect (double counting). Stated as a limitation.
2. **CA blocked by CB (82 % of cycles, per your data)** — in our scene CA and CB are separate physical lanes, so they never block each other. Deferred until after the exhibition. Your point stands: more CB green is the only lever that unblocks CA's 100 veh/15 min.
3. **The adjacent 4-way intersection is not modelled**, so our Bx delay is a **lower bound**.
4. **No U-turns, no motorcycles as separate agents, no PCU weighting.** Motorcycle effects are partly absorbed into the measured $\ell_1$ and $h$ (both above HCM defaults, largely because motorcycles filter to the head of the queue and must clear before cars move).
5. **$D$ is read once, at phase start** — vehicles arriving mid-phase do not extend that phase's $G$. This matches a real stop-line detector, but it is a modelling choice worth stating.
6. **$h$ and $\ell_1$ were measured on lane B in the morning only** and are applied to every lane. Turning lanes (Ax, Bx, CB) should in theory have a higher headway; unverified.
7. **Guard / officer manual intervention is not modelled** — you confirmed the frequency cannot be measured from the available footage (your §7.9), so this is a closed limitation rather than an open question. Any run in which an officer overrides the signal is outside the model's scope.
8. **T10 MiddayNormal is a counterfactual**: the real signal flashes amber 09:00–15:00, so this scenario compares two controllers against a period when neither is actually running. Kept intentionally, with the caveat stated.

## 10. The scene-serialization bug you caught

Worth recording, because it is a trap specific to Unity and it will recur.

Unity writes every public field of a component into the scene file at the moment the component is placed. On load, those serialized values **override the defaults written in the `.cs` file**. Editing the script alone therefore changes nothing for a component that is already in the scene.

Six fields were stale:

| Field | Scene held | Code intended |
|---|---:|---:|
| `startupLostTime` | 1 | **2.95** |
| `saturationHeadway` | 2.5 | **2.31** |
| `countingWindow` | 8 | **4** |
| `repetitionsPerScenario` | 1 | **27** |
| `simulationSpeed` | 2 | **10** |
| `a2Share` | 0.18 | **0.054** |

`repetitionsPerScenario: 1` was the worst of them: the batch would have produced **10 runs, not 270**.

`FixedController` escaped only because `ABACSceneBuilder` happened to call `fixedC.LoadABACPreset()` on every build, overwriting whatever the scene held. `AdaptiveController` and `ScenarioManager` had no such call.

**Fixed in three layers, plus the test you asked for:**

1. Scene patched; every field default now binds to a single `const`.
2. `ABACSceneBuilder` calls `LoadMeasuredPreset()` and `LoadBatchPreset()`, the way it always did for `FixedController`.
3. `Awake()` compares against the constants, auto-corrects, and logs an error — a batch cannot silently run on textbook values. `useMeasuredParameters = false` disables this for deliberate sensitivity runs.
4. **`SceneAuditTest` parses `SampleScene.unity` itself** and compares it against the code — `.unity` vs `.cs`, not `.cs` vs `.cs`. You were right that the earlier cross-file test could not have caught this. It works by reflecting over a freshly constructed component and checking *every* serialized scalar field, not just the six known ones, so the next drift is caught too. Verified against the pre-fix scene: **18 failures**. Against the current scene: clean.

`summary_all_runs.csv` also carries `StartupLostTime,SaturationHeadway` per row now, so every result line proves its own calibration.
